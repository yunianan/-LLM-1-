Patient Agent 完全入门手册

这份文档写给第一次打开这个目录的人。读完它，你应该能：

  1. 知道整个项目在做什么、每一层是谁；
  2. 知道每个 .py 文件负责什么、想改东西该动哪个文件；
  3. 会在本地把它跑起来，并看懂跑出来的结果；
  4. 知道以后接上其他层的真实代码时，要在这里改哪里、怎么写；
  5. 知道手上有一份标准数据集时，怎么把它变成一批能跑的病例（见 §13）。

本文档是自包含的：只读这一份就能上手，不需要先读 README.md。两者内容有重叠，不冲突。

一句话记住整个项目
病例（schemas/library）→ 生成器（generator）说要说什么 → 守卫（guard）检查合不合规 → 运行器（runner）调系统 API → 记录（recorder）→ 停止（stopping）→ 评测（evaluator/report）。

项目框架：先认清四条线

① 源码 patient_agent/

你的交付物。PA1–PA7 各占一个文件，另有 client/（被测系统那侧）和 llm/（患者怎么开口）。

② 病例库 scenarios/

6 例内置病例，覆盖 5 条验收场景；imported_scenarios/ 是从标准数据集生成出来的病例。

③ 测试 tests/

214 个 pytest 用例，含 5 条验收标准的端到端测试。

④ 产物 runs/

每跑一次就写这里：批量报告 + 逐轮记录。是产物不是源码，可随时删掉重跑。

只有三个「能运行」的入口——这个项目的入口是模块，不是一个能点 ▶ 的脚本，所以别去找“哪个 .py 可以右键 Run”：
① python -m patient_agent …（等价于 patient_agent/__main__.py）—— list / run / run-all；
② python tools/db_import.py … —— 把标准数据集转成病例；
③ python -m pytest（收集 tests/）—— 跑测试。
VS Code 里的三种跑法见 §2.4；逐个文件、逐个目录的注释见 §3。

130 秒理解：它到底在做什么

你们整个项目是一个五层的心理诊疗 LLM 系统：

L1 风险分级

判断有没有自伤/自杀风险，决定是否走安全路径。

L2 访谈 + 量表 + 画像

聊症状、做 PHQ-9 这类量表、生成「我理解的你」让患者确认。

L3 候选诊断

给出候选诊断，并排除不符合的（比如排除双相）。

L4 治疗

进入治疗性对话，观察改善 / 无变化 / 退出。

L5 复盘

结案，生成疗程总结、逐轮账本、脱敏历史。

这个 patient agent/ 目录，做的是「被测试的一方」——它扮演患者。
它不治病、不下诊断、不算量表分。它的工作是：拿一个写好的病例脚本，假装成一个患者，通过系统 API 和上面这个五层系统聊多轮，把每一轮对话记下来，最后对照病例里写的预期，自动判分「这轮测试过没过」。

打个比方：L1–L5 是「被测的学生」，Patient Agent 是「拿着标准答案的出题人」。

两条硬约束

来自任务说明第七节自检清单，代码里有对应实现：

  1. 不添加病例外事实——患者说的每句话都必须能在病例里找到出处（由 PA4 守卫拦）。
  2. 测试能按条件停止——危机、人工复核、目标事件覆盖、违规、轮数上限都能收尾（由 PA6 负责）。

还有一条设计原则：Patient Agent 只通过 8 个系统接口跟外界打交道（见 §9），所以「离线跑内置假系统」和「连真实编排器」是同一条代码路径，只是换了个实现。

重要：所有命令都要在 patient agent/ 这个目录下运行（即 README.md 和 pyproject.toml 所在的目录）。如果在别的目录，scenarios/ 会找不到。

2.3 跑测试

bash
python -m pytest

期望看到最后一行类似 214 passed in 0.55s（那行是 pytest 框架自己的英文输出，passed 就是「通过」，属正常）。

本机 dl-G 已经装好 pytest 了（pytest 9.1.1，连同 pluggy、iniconfig），直接 python -m pytest 就能跑，不需要任何 PYTHONPATH 补丁。
换到别的机器 / 别的环境报 No module named pytest？说明那个 Python 里没装 pytest（pytest 不是标准库）。两种解法：
① 装上（推荐，pyproject.toml 里本来就声明了这项测试依赖）：python -m pip install pytest，或 python -m pip install -e ".[test]"；
② 实在不想动环境（比如没有写权限），就临时把 pytest 所在目录挂进 PYTHONPATH。
装好之后，VS Code 左侧「测试」侧栏（烧瓶图标）才会自动发现 tests/ 的 214 个用例——没装 pytest 时那个侧栏是空的。

测试全离线、确定性、不出网、不需要 key，从任何目录启动都能跑（tests/conftest.py 用 __file__ 推导项目根，不依赖当前工作目录）。

Windows 中文乱码怎么办？见 §11 排错 FAQ。最省事的办法是加 -X utf8：python -X utf8 -m patient_agent run S03_explicit_crisis --scenario-dir scenarios。

5一次运行的生命周期（数据怎么流动）

理解这条链路，就理解了整个项目。以「跑一个病例」为例：

文件
scenarios/S01…/1.0.0.json

磁盘上的病例文件。

PA1
schemas.py

把 JSON 解析成 PatientScenario 对象；字段写错直接报错（extra="forbid"）。

PA2
library.py

读 index.json、按版本找文件、做 Schema 校验。

关键点

  • 生成器（PA3）和守卫（PA4）只跟「病例」有关，不跟「系统」有关。它们决定患者说什么、这话合不合规。
  • 运行器（PA5）是唯一碰网络/系统 API 的地方。所有跟系统的交互都收敛在这一个文件里，所以换系统只需换 client 的实现，不用动运行器。
  • 评测器（PA7）不重跑会话，只读 recorder。所以「跑一次、反复评」很便宜。

6.3 schemas.py — PA1 病例 Schema（586 行）

它负责什么：定义「一个病例可以有哪些字段」。这是整个项目的数据地基，所有「患者说的话」最终都来自这里定义的字段。

一个病例 = 七组临床字段 + 两组测试字段：

  • 临床七组：background（基本背景）/ clinical（临床事实）/ psychology（心理特征）/ risk（风险脚本）/ disclosure（披露策略）/ behavior（行为参数）/ trajectory（变化轨迹）。
  • expected（期望结果）：期望事件、期望走过的层、终止原因、要求排除的候选、轮数下限。
  • stop（停止策略）：max_turns、是否在危机/人工复核/违规时停、覆盖哪些事件即可停。
名字作用
ScenarioModel所有模型的基类，ConfigDict(extra="forbid")——写错字段名会直接报错，不会静默忽略。
SymptomFact一条症状。有 model_validator(mode="after")：present=true 必须有 utterance，present=false 必须有 denial_utterance。
ExclusionFact / ScalePlan需要排除的鉴别项 / 量表计划（answers 是 0–4 的假答案，refuse_after_items 控制拒答）。
ClinicalFacts一个 model_validator 保证 symptom_id 唯一、且至少有 1 条 present 症状。
DisclosurePolicyopening_templates（开场）/ never_disclose（绝不泄露）/ non_fact_replies（答非所问时的兜底）/ refusal_utterances 等。

  • declared_numbers() → 病例里出现过的所有数字。守卫用它查「患者有没有编造数字」。
  • text_corpus() → 把病例里所有文本拼起来，守卫/评测做「事实一致性」比对时用。

改了会怎样 & 常见改法

  • 想给病例加一个新的临床字段 → 改这里的模型，然后同步更新 scenarios/*/*.json。注意 extra="forbid"：病例里多写一个 Schema 没定义的键会直接报错。
  • 想让某类事实能被解锁得更晚 → 给对应的 RevealableFact 加 unlock_after_events（闸门机制）。
  • 想调默认轮数上限 → 改 StopPolicy.max_turns 的默认值（但生产上一般直接写在病例 JSON 里）。
这个文件是契约。改它之前先确认病例 JSON 都跟得上，否则 library.py 加载时会报错。

  • 想加一条「这类事实必须被追问」的规则 → 看 _pick_fact() 里 is_denial 的判断。
  • LLM 报错/返回空白 → 代码会自动退回参考台词，会话不会崩。

9.3 真实系统接口形态不同？写一个客户端子类

如果你们的接口路径/字段跟上面不一样（比如字段叫 reply 而不是 patient_reply，或者不是 REST 而是 WebSocket），不要改运行器。启动器只依赖抽象类 SystemApiClient，所以你只要实现这个抽象类，插进去就行。

patient_agent/client/my_orchestrator.py（完整示例）
"""把你们真实编排器包装成 Patient Agent 认识的 SystemApiClient。

接口形态不同时，就在这一层做「翻译」，运行器与生成器完全不用动。
"""
from __future__ import annotations

import json
import urllib.request

from patient_agent.client.base import (
    DevState,
    EpisodeSummary,
    ProfileDecision,
    RouteInfo,
    SessionHistoryItem,
    SessionSnapshot,
    SystemApiClient,
    TurnResponse,
    new_session_id,
)
from patient_agent.errors import ErrorCode


class MyOrchestratorClient(SystemApiClient):
    """假设你们的服务跟 http_client 的形态不同：字段是 reply 而非 patient_reply，
    且用 /api/v2/ 前缀。"""

    name = "my_orchestrator"

    def __init__(self, base_url: str, timeout: float = 30.0, token: str = "") -> None:
        self.base_url = base_url.rstrip("/")
        self.timeout = timeout
        self.token = token

    # ---------------------------------------------------------- 内部工具
    def _post(self, path: str, payload: dict) -> dict:
        req = urllib.request.Request(
            f"{self.base_url}{path}",
            data=json.dumps(payload).encode("utf-8"),
            headers={"Content-Type": "application/json", **self._auth()},
            method="POST",
        )
        with urllib.request.urlopen(req, timeout=self.timeout) as resp:
            return json.loads(resp.read().decode("utf-8"))

    def _get(self, path: str) -> dict:
        req = urllib.request.Request(
            f"{self.base_url}{path}", headers=self._auth(), method="GET"
        )
        with urllib.request.urlopen(req, timeout=self.timeout) as resp:
            return json.loads(resp.read().decode("utf-8"))

    def _auth(self) -> dict:
        return {"Authorization": f"Bearer {self.token}"} if self.token else {}

    # -------------------------------------------- ★ 把你的响应翻译成 TurnResponse
    def _to_turn(self, raw: dict, session_id: str) -> TurnResponse:
        """这是适配层唯一需要动脑的地方：字段名对不上就在这里翻译。"""

        route_raw = raw.get("route") or {}
        item_raw = raw.get("scale_item") or None
        return TurnResponse(
            session_id=session_id,
            patient_reply=raw.get("reply", ""),          # 你们叫 reply
            waiting_type=raw.get("wait", "none"),        # 你们叫 wait
            route=RouteInfo(
                main_layer=route_raw.get("layer", "L2"),
                secondary_layers=route_raw.get("also", []),
                intent=route_raw.get("intent", ""),
                reason=route_raw.get("why", ""),
            ),
            scale_item=None if item_raw is None else {
                "scale_name": item_raw["name"],
                "item_number": str(item_raw["no"]),
                "prompt": item_raw["text"],
                "min_score": item_raw.get("lo", 0),
                "max_score": item_raw.get("hi", 3),
            },
            events=raw.get("events", []),
            error_code=(ErrorCode(raw["error"]) if raw.get("error") else None),
            error_message=raw.get("error_msg", ""),
            session_ended=raw.get("ended", False),
            termination_reason=raw.get("stop_reason"),
        )

    # ------------------------------------------------------------- 8 个接口
    def create_session(self, *, locale="zh-CN", channel="test", session_id=None):
        raw = self._post("/api/v2/session", {"locale": locale, "channel": channel})
        return SessionSnapshot(
            session_id=raw["sid"],
            route=RouteInfo(main_layer="L1", intent="intake", reason="新建"),
            initial_prompt=raw["hello"],
            locale=locale,
        )

    def send_message(self, session_id: str, text: str) -> TurnResponse:
        raw = self._post(f"/api/v2/session/{session_id}/say", {"text": text})
        return self._to_turn(raw, session_id)

    def confirm_profile(self, session_id: str, decision=ProfileDecision.CONTINUE, notes=""):
        value = decision.value if isinstance(decision, ProfileDecision) else str(decision)
        raw = self._post(f"/api/v2/session/{session_id}/profile", {"decision": value, "notes": notes})
        return self._to_turn(raw, session_id)

    def submit_scale(self, session_id: str, item_number: str, score: int, answer_text=""):
        raw = self._post(
            f"/api/v2/session/{session_id}/scale",
            {"item_number": item_number, "score": score, "answer_text": answer_text},
        )
        return self._to_turn(raw, session_id)

    def set_pause(self, session_id: str, paused: bool) -> TurnResponse:
        raw = self._post(f"/api/v2/session/{session_id}/pause", {"paused": paused})
        return self._to_turn(raw, session_id)

    def get_dev_state(self, session_id: str) -> DevState:
        raw = self._get(f"/api/v2/session/{session_id}/state")
        return DevState(**raw)

    def get_episode_summary(self, session_id: str):
        raw = self._get(f"/api/v2/session/{session_id}/summary")
        return None if not raw else EpisodeSummary(**raw)

    def get_session_history(self, session_id: str | None = None):
        raw = self._get("/api/v2/sessions")
        items = raw if isinstance(raw, list) else raw.get("items", [])
        results = [SessionHistoryItem(**item) for item in items]
        return [i for i in results if session_id is None or i.session_id == session_id]

  1. 在 client/base.SystemApiClient 加一个 @abstractmethod（改契约）。
  2. 两个实现都要补：mock_system.py 和 http_client.py（以及你自己的子类）。
  3. 在 runner.py 里调用它——通常加进 _collect_artifacts()，把结果存进 recorder。
  4. 补测试：tests/test_mock_system.py 的 SYSTEM_API 列表和签名一致性测试会自动要求 mock 实现新接口。
三步改法
# 1) patient_agent/client/base.py
class SystemApiClient(abc.ABC):
    ...
    @abc.abstractmethod
    def get_evidence_chain(self, session_id: str) -> list[dict]:
        """新增：读 L3 的证据链明细（示例）。"""

# 2) patient_agent/client/mock_system.py
    def get_evidence_chain(self, session_id: str) -> list[dict]:
        session = self._get(session_id)
        return session.candidates + session.excluded

# 3) patient_agent/runner.py 的 _collect_artifacts() 里
    try:
        self.recorder.evidence_chain = self.client.get_evidence_chain(sid)
    except PatientAgentError:
        pass  # 老系统没这个接口时不致命
SystemApiClient 用的是 abc.ABC，一旦加了 @abstractmethod，所有没实现的子类都会无法实例化——这正是我们想要的「契约漂了就立刻报错」。

11排错 FAQ

Q1：控制台中文变成 �� 或乱码。

Windows 控制台默认用 GBK。三种办法（任选）：

  • 加 -X utf8（最省事）：python -X utf8 -m patient_agent run S01_low_risk_depression --scenario-dir scenarios
  • 设环境变量：set PYTHONUTF8=1（cmd）或 $env:PYTHONUTF8=1（PowerShell）
  • 直接用 patient-agent 命令（cli.py 里有 _force_utf8_stdout() 会强制 UTF-8）。
Q2：FileNotFoundError、找不到病例，或 [SCHEMA_ERROR] 病例库目录不存在：scenarios。

八成是没在 patient agent/ 目录下运行。所有命令的正确工作目录是含 pyproject.toml 的那个目录。

注意路径补丁只解决「导包」，不解决「找数据」：scenarios/ 是按当前工作目录找的，从别的目录跑就会报 [SCHEMA_ERROR] 病例库目录不存在：scenarios。要么先 cd 到项目根，要么用 --scenario-dir 或环境变量 PATIENT_AGENT_SCENARIO_DIR 指过去。

Q3：ModuleNotFoundError: No module named 'patient_agent'。

几乎都是直接按路径跑了 .py 文件，而不是用 -m 跑模块。下面这种写法一定失败：

bash（错误写法）
& D:\miniconda\envs\dl-G\python.exe "...\patient agent\patient_agent\__main__.py"
# ModuleNotFoundError: No module named 'patient_agent'

原因：直接跑文件时，Python 把 sys.path[0] 设成那个文件自己的目录，也就是 patient_agent\。于是它跑到 patient_agent\ 里面去找一个叫 patient_agent 的包——当然找不到（包不在它自己里面）。换成 -m patient_agent 时，sys.path[0] 变成当前工作目录，也就是项目根，包就在那儿。

正确写法（先 cd 到项目根，即含 pyproject.toml 的目录）：python -m patient_agent list。

VS Code 的 Run Python File 按钮干的正是「按路径跑文件」，所以它必然报这个错——要么改用集成终端，要么配 launch.json 的 "module" 字段（见 §2.4）。

实在想保留「跑文件」的写法，就先手动把项目根塞进去：$env:PYTHONPATH = (Get-Location).Path，再跑。测试没这个问题——pytest.ini 里的 pythonpath = . 已经替你处理好了。

Q4：ModuleNotFoundError: No module named 'pydantic'。

没装依赖。pip install pydantic pytest。

Q5：改了病例 JSON，一跑就报错。

多半是字段名写错或多了 Schema 没定义的键——extra="forbid" 会直接报错。对照 schemas.py 里的字段名检查。这是故意设计的：宁可报错，也不静默忽略。

Q6：pytest -q 跑完没有汇总行。

pytest.ini 里已经有 addopts = -q，再传 -q 就变成 -qq，会把汇总藏掉。直接跑 python -m pytest 就行（不加 -q）。

Q7：评测没过（[FAIL]），怎么定位？

看 report.md 的「失败详情」，或者用 --verbose：python -m patient_agent run-all --verbose --only S05_comorbid_anxiety_depression。它会打印这一例的 8 项判分明细。

Q8：改了病例台词，测试结果变了。

正常——这就是为什么要版本化病例。新增一个版本文件，别就地覆盖，这样「当时用的是哪一版」永远可追溯。

Q9：想连真模型但报「配置有问题」。

llm_mode=api 必须有 OPENAI_API_KEY；system_api_mode=http 必须有 SYSTEM_API_BASE_URL。这是 config.validate() 故意拦的。

Q10：runs/ 能删吗？

能。它是产物目录，随时可删、重跑即可再生成。它不属于源码。

13用标准数据集批量生成病例

这一节回答：「我手上有一份标准数据集，怎么把它变成这个模型能跑的病例？」

结论、步骤、命令、坑，都在这里。配套的工具是 tools/db_import.py（只用 Python 标准库，不新增任何依赖）。

13.1 先记住一件事：模型不吃数据集

Patient Agent 启动时只做一件事：打开病例库目录（默认 scenarios/），读 index.json， 再把每个 <id>/<版本>.json 交给 PA1 的 Schema 校验（见 §6.3）。

它不会连数据库，不会读 CSV，也不需要知道你的表结构。所以「用数据集当病例」在代码层面只有一种含义：

写一个转换器，把数据集里的记录物化成符合 Schema 的 JSON 文件，放进病例库目录。

tools/db_import.py 就是这个转换器的最小可用版。它做三件事：

  1. 把库里的记录映射成病例的七组临床字段；
  2. 用标准词表模板补出「患者会说的每一句话」；
  3. 按风险等级与治疗反应推导期望路径（expected / stop），然后真的把这条病例跑一遍，用中文告诉你过没过。

13.2 数据集可以长什么样

形态怎么喂进去
结构化导出（JSON）--source 你的.json，内容是 {"dataset_version":"...","records":[...]} 或直接一个数组
SQLite / SQL 导出--source 你的.sqlite --table records（一行一条记录）
CSV--source 你的.csv（第一行是表头；symptoms 这类嵌套字段写成 JSON 文本放在单元格里）
自由文本病历不能直接喂，要先做信息抽取，见 §13.12
会谈记录（一问一答）--source 你的.json，内容是 [{"conversation":[{"doctor":…,"patient":…}, …]}, …]。自动识别，走反向抽取，见 §13.2.1

13.2.1 会谈记录格式：只有「医生问 / 患者答」的原始文本

最常见的一类数据就是这种——没有任何结构化字段，只有一问一答的逐轮原话。它不用先转成 §13.3 的规范化记录， 直接喂给同一个命令即可，转换器按结构自动认出它（不靠文件名）。

你的会谈记录.json
[
  {
    "conversation": [
      {"doctor": "最近有没有觉得情绪低落，或者提不起兴趣？", "patient": "最近情绪还算稳定，但有时候还是会感到焦虑和紧张。"},
      {"doctor": "睡眠怎么样？有没有入睡困难或者早醒？",       "patient": "睡眠还可以，没有特别明显的入睡困难。"},
      {"doctor": "有没有过想伤害自己或者自杀的念头？",         "patient": "没有，我没有过这种念头。"}

]

三条硬性约定，不符合就认不出来：

  • 键名必须叫 doctor / patient（q/a、role/content 之类都不认）；
  • 最外层要是数组，或带 records 字段的对象（{"records":[…]}）；单个裸对象不接受；
  • 一个元素 = 一次会谈 = 一个病例，自动编号 TRANSCRIPT_00、TRANSCRIPT_01…

它抽得出什么、抽不出什么

判断「医生这句话在问什么」靠的是一张内置话题表：26 条（15 个症状话题、6 个背景话题、4 个鉴别话题、1 个风险话题）， 落到 11 个症状码和 3 个鉴别码上。命中的就能抽，命不中的不会丢——原话会暂存成背景事实并进待办。

内容怎么来的
自动抽出开场陈述、阳性症状、被否认的筛查项（→ 阴性鉴别条件）、风险否认句、背景事实（家族史 / 婚恋 / 工作 / 性格…）问句匹配话题表 + 回答分级（否认 / 承认）
留空待补量表作答、expected 路径、终止原因、风险等级、probe_keywords 校准会谈记录反推不出来，一律不猜，逐条列进「待人工补齐」

开场陈述取第一条患者原话，并把它提到的症状标成 disclosure="proactive"， 保证前几轮系统就能识别到（原理见 §13.6）。

抽取是关键词启发式，所以：问法和内置触发词越接近，命中越多；换一家医院换一套问法，人工补的量会明显变大。

先摸覆盖率：上面第 ① 步 --dry-run 打印出的「待人工补齐」条数越多，说明问法离内置触发词越远。 该给话题表补词，就改 tools/db_import.py 里的 SCREENING_TOPICS（同 §13.11 的改法）。

另外两个已知的取舍，用之前心里有数：

  • 严重度是粗判：回答里出现「每天 / 一直 / 完全」这类高频词就记 severity=2，否则 1，duration 一律 unknown——请人工改判。
  • 家族史里的诊断名（例如「我父亲被诊断为精神分裂症」）会被自动加进白名单并留一条警告， 因为守卫只认「医生说 / 医院说」这类转述前缀，认不出「我父亲被诊断为」。这条人工必核：万一是患者自评而非转述，要删掉白名单。

scenario_id指定病例 ID，不写自动生成默认 DB_<record_id>
version / title / description版本与说明版本默认取 dataset_version
age_range / occupation / family_relationship / major_events背景—
chief_complaint主诉，会进开场陈述不写给一句通用开场
onset病程起点"3个月"，会被填进症状 duration
denied_conditions需要被排除的条件默认 ["manic_history","psychotic_features"]
scale_items量表逐题作答不写就按症状自动推导
risk_screen风险筛查等级none（默认）
treatment_response治疗期走向stable（默认）
expected_diagnosis_codes / must_not_diagnose期望 / 禁止的诊断码[]
termination_reason显式指定期望终止不写=按推导；写 null=期望不终止

三个容易忽略的点：

  • symptoms 里的 0 不是「没记录」，而是「被问过但不存在」：它会变成一条 present=false + denial_utterance 的事实。这正是被测系统问「有没有过特别兴奋…」时，患者应当否认的依据。
  • scale_items 不写就自动推导：命中了哪条症状，就上对应量表（内置 6 份：PHQ-9 / GAD-7 / PCL-5 / Y-BOCS / MDQ / ISI），逐题分值由严重度映射，题数不足的部分补 0。
  • risk_screen 填到 explicit_ideation 及以上，患者开场就是危机陈述，系统会走 L1 安全路径直接结案——这就是验收场景 3 那条用例；此时「治疗反应」不再影响终止原因。

risk_screen 取值：noneambiguousexplicit_ideation / plan / immediate_crisis

treatment_response 取值：improvingno_changedropout / stable

13.5 第 3 步：分清「机器填的」和「你必须改的」

以真实生成的 imported_scenarios/DB_P0001/2026.1.json 为例。

机器能填对的（不用管）

病例里的位置从哪来
clinical.symptoms[] 清单、severity、duration数据集
clinical.scale_plans[].answers严重度 → 量表逐题分值
risk.level + disclosure.never_discloserisk_screen（比本等级更重的话术整串禁掉，防止患者自己把风险说升级）
background.*、clinical.timeline_anchors、clinical.must_not_diagnose数据集
clinical.exclusions[].denial_utterancedenied_conditions + 内置词表

必须你动手的三处

  1. 每一句话：symptoms[].utterance、denial_utterance、disclosure.opening_templates、trajectory.steps[].utterance。 现在是 "3个月了，情绪一直很低落，心里堵得慌。" 这类模板句——事实对、口气假。 这份病例的临床准确性来自数据集，但像不像一个真人在说话只能靠你改这几句。 注意每条 utterance 里必须带着被测系统认得的症状词（见 §13.6 的错误示例）。
  2. probe_keywords：决定「系统问到什么话时患者才说这条事实」，是最容易静默翻车的地方，见 §13.6。
  3. expected / stop：数据集完全没有「我期望系统怎么表现」，见 §13.8。

13.6 命门：probe_keywords 必须和被测系统的问法对齐

患者说什么不是模型自由发挥的，而是 PA3 按「系统上一句说了什么」挑事实（见 §6.5）：

挑 probe_keywords 命中系统这句话的事实；命中数多的优先；都没命中时，才轮到标了 disclosure="proactive" 的事实主动说出来。

所以一条症状能不能被说出来，取决于它的 probe_keywords 和被测系统实际问的话有没有交集。 内置 Mock 与内置病例是这么对上的（可以直接照着抄）：

事实probe_keywords系统的哪句话会把它勾出来
情绪低落["具体","难受","低落"]「你愿意说说最近具体是什么让你这么难受吗？」
睡眠维持困难["睡眠","精力"]「除了情绪，睡眠或者精力上有没有什么变化？」
自我价值感低["不够好","觉得自己"]「你有没有觉得自己哪里做得不够好？」
躁狂史（否认）["兴奋","不需要睡觉","话也特别多"]「有没有过一段时间特别兴奋、不需要睡觉、话也特别多？」
精神病性症状（否认）["听到","看到","别人没有察觉"]「有没有听到或者看到别人没有察觉的东西？」

填错的后果是「静默失败」：症状说不出口 → 系统识别不到 → 量表不启动 → l2_scale_completed 观测不到 → 评测里 required_events 失败。 系统一句报错都不会给，你只能从评测结论倒推。

还有一个真实踩过的坑：易激惹必须先进入系统视野，双相排除才有机会发生。 被测系统只有在识别到「易激惹」之后，才会问那道「有没有过特别兴奋…」的鉴别题， 也才会把双相放进 excluded。而 L2 正式访谈只有寥寥几轮就会被量表接管， 靠追问关键词不保证说得到——内置的 S04 的做法是把易激惹写进开场陈述。 tools/db_import.py 也是这么做的：只要有易激惹，就把它的台词并进 disclosure.opening_templates[0]。

13.7 第 4 步：放进病例库、跑起来、怎么算「真的成了病例」

bash
# ① 能被认得（index.json 与 Schema 都过了）
python -m patient_agent list  --scenario-dir imported_scenarios

# ② 能逐轮对话（台词与关键词驱动得动系统）——run 自带逐轮打印，没有 --verbose
python -m patient_agent run DB_P0001 --scenario-dir imported_scenarios

# ③ 评测通过（期望路径成立）→ 退出码 0（--verbose 是 run-all 的选项）
python -m patient_agent run-all --scenario-dir imported_scenarios --verbose

这三条命令里的 --scenario-dir 其实可以省掉：项目根 .env 已经把默认病例库指到了 imported_scenarios/，所以直接 python -m patient_agent list 读的就是生成库（见 §13.13）。

「成了病例」的三个判据：能被 list 列出来 → 能被 run 逐轮跑 → run-all 评测通过。

实测：随仓库带的 imported_scenarios/ 里有 4 条演示用例（低风险改善 / 焦虑共病无变化 / 明确危机 / 主动退出），分别 24 / 24 / 1 / 21 轮，4/4 评测通过，run-all 退出码 0。 新增 tools/ 与 imported_scenarios/ 两个目录不影响原有测试：214 个用例仍全过。

13.8 expected / stop：手写，还是用 --baseline 冻基线

expected 是这份病例的「标准答案」。三条路：

做法怎么做代价
按临床意图手写直接改 expected.events / expected_layers / termination_reason / stop.max_turns得想清楚「这份病例到底想验证什么」——这是标准做法
用推导值（默认）转换器按风险等级 + 治疗反应生成是通用骨架，未必等于你的意图
--baseline 冻结观测--baseline 跑一遍，把观测到的事件、层、终止原因写回 expected，其余事件记为可选如果被测系统本身就是错的，基线会把错的行为锁死

所以正确姿势是：调试阶段用 --baseline 快速拿到一条能过的用例，定稿前回头逐项确认「这真是我想断言的行为」。

13.9 版本与可追溯

同一个 scenario_id 改了台词，新增版本文件，不要就地覆盖—— 改一句台词就可能改变「不迎合」这类结论，测试报告必须能追到「当时用的是哪一版」。 转换器会：

  • 每次写盘都自动维护 imported_scenarios/index.json（登记 versions、更新 latest）；
  • 目标版本文件已存在时直接报错，提示你换 --version 或加 --force（不推荐，会丢掉旧版本）。

13.10 排错：实际踩过的四个坑

现象原因怎么办
required_events 缺 l2_scale_completed症状一条都没被说出来，系统认为没东西可查，跳过了量表检查 probe_keywords 是否和系统问法对得上；必要时把核心症状设成 proactive 或写进开场陈述
required_events 缺 l3_candidate_excluded，或 excluded_conditions 未排除双相系统没识别到「易激惹」，也就没问那道躁狂鉴别题把易激惹写进 opening_templates（转换器已自动做）
termination 不符轨迹步数不够，系统走到治疗周期上限才结案，终止原因和你期望的不一样「改善」至少 2 步积极表述、「无变化」至少 3 步消极表述（转换器默认给 3 步）
新版病例写不出去同一版本文件已存在换 --version（推荐），或 --force

13.11 换成你自己的数据集：只改映射表

tools/db_import.py 里需要改的只有三个地方：

  1. CATALOG —— 症状 code → label / utterance / denial_utterance / probe_keywords。 数据集用了别的症状命名（比如 ICD / DSM 编码），就在这里加条目。当前内置 11 个 code： depressed_mood、anhedonia、insomnia、fatigue、worthlessness、concentration_difficulty、 anxiety、irritability、trauma_related、obsession_compulsion、elevated_mood。
  2. EXCLUSION_CATALOG 与 SCALE_CATALOG + SCALE_INDICATION —— 鉴别项与量表。 ⚠️ SCALE_INDICATION 必须和被测系统的量表指示表一致，否则会出现「系统要做某份量表、 病例里却没有作答计划」，量表链路永远走不完。
  3. build_scenario() —— 字段映射本身。数据集的列名不同就改这里 （或者更省事：在你那一侧先把列名改成 §13.3 的规范化字段名）。

数据源的读取逻辑在 load_source()。要接 MySQL / PostgreSQL，就在那里加一个分支 （sqlite3 / json / csv 都是标准库，别的数据库要额外装驱动）。

13.12 如果数据集是自由文本（不是结构化字段）

那这条链路要多一步信息抽取：主诉、病程、症状、鉴别筛查结果、量表分， 都得先从文本里抽出来，才能谈映射。

可行做法是先用 LLM 把文本抽成 §13.3 的规范化记录，再喂给转换器。 但请注意：这一步的准确性风险远高于格式转换（抽错一条症状，整条病例的临床事实就是错的）， 所以先在小样本上人工核对抽取结果，再批量跑。

13.13 两套病例库怎么并存：内置基线 + 数据集生成

约定：内置的 scenarios/ 只增不减。它不是脚手架，而是 PA2 的交付物本身， 也是 5 条验收场景的自动化证据，同时被 8 个测试文件、上百处引用依赖着 （tests/conftest.py 里 SCENARIO_DIR 硬编码指向它）。 数据集生成的病例一律另放一个目录，两者用 --scenario-dir 切换，互不干扰。

库内容谁来维护
scenarios/（默认）6 例内置病例，对应 5 条验收场景，人工按临床意图写好 expected只增不减。是验收基线，测试和 run-all 默认跑它
imported_scenarios/数据集（含会谈记录）生成出来的病例，DB_* / TRANSCRIPT_*日常新增都往这里放

默认读哪一套由 .env 决定。项目根目录的 .env 里这一行把默认病例库指到了生成库：

.env
PATIENT_AGENT_SCENARIO_DIR=imported_scenarios

所以不带 --scenario-dir 时，list / run / run-all 读的是数据集生成的病例， 而不是内置的 6 例。想看内置基线时显式指回去即可。优先级是 --scenario-dir 参数 > 真实环境变量 > 项目根 .env > 代码默认值 scenarios（见 §6.14 config.py）。

bash
# 默认：读数据集生成的病例（imported_scenarios/）
python -m patient_agent list
python -m patient_agent run-all --out runs/imported

# 显式指回内置 6 例（验收基线）
python -m patient_agent run-all --scenario-dir scenarios --out runs/builtin

# 想改默认值：编辑项目根 .env 的 PATIENT_AGENT_SCENARIO_DIR；
# 删掉那一行就回到内置 scenarios/
删掉 .env 里那一行会怎样？默认库就回到内置 scenarios/（代码默认值）。 这个开关只影响「默认读哪个目录」，--scenario-dir 永远能覆盖它。

两套的日常循环是：数据集 → 转换器 → 生成库 → 跑评测，内置库只在需要复核验收标准时才跑。

想让某条生成病例「转正」进内置主库：把 imported_scenarios/TRANSCRIPT_00/ 整个复制到 scenarios/S07_xxx/，再去 scenarios/index.json 登记一条 （scenario_id / versions / latest / title / tags / description）， 改法同 §8 的「新建一个病例」。

测试不受这个开关影响。tests/conftest.py 里的 SCENARIO_DIR 硬编码指向 scenarios/，所以 pytest 永远跑内置 6 例——这是故意的：验收证据不能跟着日常配置漂移。
一句话：内置库负责「证明系统能满足验收标准」，生成库负责「用真实/批量数据扩充覆盖」。 两者物理隔离、各自成库，默认读哪一套由 .env 一行决定。
